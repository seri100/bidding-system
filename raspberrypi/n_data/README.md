## 현재 동작

API에 공동도급지역이 비어 있고 양수 비율 또는 의무 플래그가 있는 공고만 나라장터 상세화면에서 보완한다. 공고번호와 차수를 확인한 뒤 수신자 판정 전에 원문과 정규화 행을 갱신한다.

- 1회 최대 1건, 브라우저 작업 240초 한도, 성공 캐시 6시간.
- 실패 건은 발송을 보류하고 다음 수집 주기에서 재시도한다. API 조회 시간창 밖에서도 대기열을 복구한다.
- 입찰 마감 또는 7일 경과 건은 대기열에서 제거한다.
- 취소공고는 기존 취소 처리 경로를 사용한다.
- 참가가능지역·현장·기관 지역을 공동도급지역으로 대체하지 않는다.
- 기존 수신자 설정, 예약 타이머와 중복발송 기록은 유지한다.

운영: `/home/pi/n_data`, 산출·상태: `/mnt/vol1/bid/n_data`.
검증 환경: Raspbian 10 armv7l, Python 3.7.3, Selenium 4.9.1, Chromium/ChromeDriver 92.0.4515.98.
기존 Selenium과 시스템 브라우저를 사용한다. Node/Playwright나 OS 업그레이드는 이번 해결에 필요하지 않았다.

## 공개 저장소의 코드 범위

`g2b_joint_region.py`는 적용한 보완 모듈 원문이다. 운영 발송 모듈에는 전화번호가 포함되어 있어 전체 운영 ZIP과 기존 대형 소스는 게시하지 않는다. 대신 두 파일의 변경 사항을 [읽을 수 있는 패치](patches/20261023-joint-region.patch)와 해시로 검증하는 재구성 데이터로 관리한다. 인증키·수신자 설정·로그·중복가드 DB는 저장소 밖에서 관리한다.

운영 백업 원본으로 검토용 전체 소스를 재구성할 때:

```bash
python3 raspberrypi/n_data/prepare_sources.py \
  --original-dir /home/pi/n_data/backup_joint_web_20261023_200053_641643 \
  --output-dir /home/pi/n_data_joint_review
```

이 명령은 원본 해시를 확인하고 별도 검토 폴더만 만든다. 운영 파일을 교체하거나 발송하지 않는다. 운영 원본이 없는 GitHub 단독 체크아웃만으로는 전체 발송 프로그램을 복원할 수 없다.

이미 운영에 적용했으므로 다시 설치할 필요는 없다. `apply_update.py`는 재구성된 전체 소스와 원본 해시, 실제 두 공고의 15분 이내 조회 결과, 운영과 같은 flock 잠금이 확보되어야 적용한다. 현재 운영본은 원본 해시와 달라 중복 적용이 거절된다.

## 오프라인 확인

```bash
python3 -m unittest discover -s raspberrypi/n_data/tests -v
```

브라우저·API 키·알림톡·캘린더 연결 없이 공고/차수 검증, 지역값 충돌 거부, 캐시, 실패 보류·재시도, 취소 경로와 진단/상태 읽기 전용 동작을 확인한다. PR의 자동 검사도 같은 오프라인 검사만 수행하며 운영 배포는 하지 않는다.

## 운영 상태 읽기 전용 점검

```bash
python3 /home/pi/n_data/joint_region_status.py
python3 /home/pi/n_data/joint_region_status.py --json
```

대기 공고번호, 시도 횟수, 대기 시간, 마지막 오류 종류와 실패 단계를 표시한다. 기본 주의 기준은 **3회 이상 실패 또는 60분 이상 대기**다. `--warn-attempts`, `--warn-age-minutes`로 바꿀 수 있다. 입찰 마감이 지난 대기도 주의 대상으로 표시한다.

종료 코드: 0 정상, 1 주의 대상 있음, 2 상태 미생성·손상·읽기 실패. 빈 대기열과 상태 파일을 읽지 못한 상황을 구분한다. 이 도구는 상태를 수정하거나 브라우저·API·발송을 실행하지 않는다. 자동 발송되는 경고나 추가 스케줄은 만들지 않는다.

보완 실패는 대기 항목의 `last_error`, `last_stage`와 `[JOINT_WEB][RETRY] ... stage=...`에 남는다. 예: `search_results` 검색 결과 대기, `detail_open` 상세 열기, `detail_read` 상세 읽기, `detail_validate` 공고·지역·비율 검증. 기존 상태 파일의 과거 실패는 단계가 미기록일 수 있으며 다음 실패부터 기록된다. 오류 전문·전화번호·원문 행은 점검 출력에 포함하지 않는다.
