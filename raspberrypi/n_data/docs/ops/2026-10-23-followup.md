# 2026-10-23 Issue #1 후속 점검 및 진단 개선

## 운영 확인

20:42 KST 읽기 전용 점검에서 서비스의 마지막 실행은 20:30:04~20:30:37, Result=success, timer active였다. 일별 실제 프로그램 로그 `logs/run_20261023.log`에서 20:15, 20:30 실행의 `[MAIN] END`를 확인했다. 셸 출력 파일 `run_main_send.log`만 보면 프로그램 로그를 놓칠 수 있어 일별 로그를 기준으로 점검했다.

적용한 3개 파일은 기존 manifest의 해시와 일치했다. 20:49:30 KST 상태 파일은 cache=0, pending=0이었고 점검한 최근 로그 범위에는 FATAL/API 오류/보완 재시도/보완 timeout이 없었다. 보완 대상이 없었으므로 이 관측을 새 누락 공고의 실제 알림톡 수신 성공으로 해석하지 않는다.

## 이번 개선

- 브라우저 시작, 메인 진입, 검색 전환, 검색 종류 선택, 번호 입력, 검색 실행, 검색 결과, 상세 열기/읽기, 값 검증의 단계를 구분한다.
- 실패한 대기 항목에 `last_error`, `last_stage`를 저장하고 재시도 로그에도 남긴다. worker 전체 timeout이면 마지막으로 출력한 단계를 사용한다.
- 예외 전문 대신 오류 종류와 정해진 단계명만 기록한다.
- `joint_region_status.py`는 상태 파일을 읽어 대기 횟수/시간/마지막 단계와 캐시 건수를 표시한다. 기본 주의 기준은 실패 3회 또는 대기 60분이며, 마감이 지난 대기도 표시한다.
- 종료 코드는 정상 0, 주의 1, 상태 미생성/손상/읽기 실패 2다. 상태 손상을 빈 정상 대기열로 오인하지 않는다.
- 점검 도구는 API·브라우저·발송을 호출하지 않으며 상태를 갱신하지 않는다. 추가 경고 메시지/스케줄은 생성하지 않았다.

기존 발송 필터·수신자·중복가드·타이머는 변경하지 않았다. API 전체 누락 감지나 OS 교체는 이번 변경에 포함하지 않는다.
