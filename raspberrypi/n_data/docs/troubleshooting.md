# 문제가 생겼을 때 GitHub로 확인하고 개선하는 절차

## 1. Issue #1에서 시작하기

[Issue #1](https://github.com/seri100/bidding-system/issues/1)을 즐겨찾기한다. 문제가 생기면 최근 날짜의 진행 내용과 미완료 체크 항목을 먼저 확인한다. 과거의 정상 기록은 현재 상태를 보장하지 않는다.

- Issue #1: 증상, 진행 상황, 남은 확인 사항.
- [PR #2](https://github.com/seri100/bidding-system/pull/2): 변경 파일과 검사 결과. `Files changed`는 변경 내용, `Checks`는 자동 검사 결과다.
- [README](../README.md): 프로그램 동작과 점검 명령.
- [장애 기록](incidents/2026-10-23-joint-region.md), [후속 적용 기록](ops/2026-10-23-followup.md), [manifest](../manifest.json): 원인, 적용 시각, 백업 및 파일 해시.

GitHub 검사의 초록색 성공은 오프라인 검사 통과를 뜻한다. 라즈베리파이 실행이나 실제 알림톡 수신 성공을 뜻하지 않는다. PR 병합도 자동 배포가 아니다. 문서가 기본 브랜치에서 안 보이면 Issue에 있는 고정 커밋 링크로 연다.

## 2. 문제 정보를 모아 ChatGPT에 전달하기

다음 양식을 복사해 보내면 된다. 알 수 없는 항목은 ‘모름’으로 두어도 된다.

```text
GitHub Issue #1 기준으로 확인하고 개선을 이어가자.
https://github.com/seri100/bidding-system/issues/1
발생 시각(한국시간):
공고번호와 차수:
공고명:
문제: 지역 공란 / 알림 미수신 / 중복 수신 / 기타
기대했던 내용:
실제 받은 내용:
범위: 특정 공고만 / 전체 알림 / 모름
최근 변경한 내용:
원격 연결 상태: 연결됨 / 연결 필요 / 모름
먼저 읽기 전용으로 원인을 확인하고 결과를 Issue에 기록해줘.
```

현재 대화에서는 알림 내용을 전달할 수 있다. 공개 Issue에는 전화번호·인증키·접속 주소·수신자 정보와 원본 로그/DB/전체 ZIP을 올리지 않는다. 공개 기록에는 필요한 공고번호, 시각, 오류 종류와 단계만 남긴다. 연결이 필요하면 그때 필요한 작업만 안내받는다.

## 3. 운영 상태를 읽기 전용으로 확인하기

직접 실행하고 싶을 때만 라즈베리파이 터미널에 아래 명령을 붙여 넣는다. Python 코드를 셸에 한 줄씩 입력할 필요는 없다.

```bash
python3 /home/pi/n_data/joint_region_status.py
```

| 출력/종료 코드 | 의미와 다음 조치 |
|---|---|
| `ok` / 0 | 점검한 상태 파일 기준으로 주의 대상 없음. 대기 0건이어도 모든 공고의 발송 성공을 보장하지 않으므로 해당 공고를 따로 확인한다. |
| `attention` / 1 | 기본 기준으로 실패 3회 이상, 대기 60분 이상 또는 마감 경과. 공고번호·시도 횟수·마지막 오류/단계를 전달한다. |
| 오류 / 2 | 상태 파일 미생성·손상·읽기 실패. 정상적인 빈 대기열로 판단하지 않는다. |

담당 작업자는 타이머, 마지막 서비스 실행, 실제 일별 로그, 공고별 대기 상태와 운영 파일 해시를 함께 확인한다.

```bash
systemctl show main_send.timer -p ActiveState -p NextElapseUSecRealtime
systemctl show main_send.service -p ActiveState -p Result -p ExecMainStartTimestamp -p ExecMainExitTimestamp
```

`main_send.service`는 실행 후 끝나는 oneshot이므로 대기 중 `inactive`가 정상일 수 있다. 실행 종료 시각과 `Result=success`, `/home/pi/n_data/logs/run_YYYYMMDD.log`의 `[MAIN] END`를 함께 확인한다. 실행 중 표시되는 이전 결과만으로 이번 실행의 성공을 판단하지 않는다. `run_main_send.log`만 보면 실제 프로그램 로그를 놓칠 수 있다.

| 증상 | 우선 확인할 것 |
|---|---|
| 비율은 있는데 공동도급지역 공란 | 해당 공고번호·차수, 보완 대기 여부, `last_error`·`last_stage`, 상세화면 값 |
| 전체 알림이 멈춤 | 타이머, 최근 실행 시작/종료, 일별 로그, API 오류 |
| 특정 공고만 미수신 | API 수집 여부, 보완 보류, 수신 조건, 기존 발송 기록 |
| 같은 공고가 중복 수신됨 | 공고 차수·변경공고 여부와 중복가드 기록. 기록을 지우지 않고 조사 |
| GitHub 검사 실패 | 실패한 검사 로그와 변경 파일. 운영 장애 여부는 별도 확인 |

점검 목적으로 발송 서비스를 수동 실행하거나 중복가드를 삭제하지 않는다. GitHub 파일이나 ZIP을 운영 폴더에 바로 덮어쓰지 않는다.

## 4. GitHub에 기록하고 수정하기

같은 문제의 후속 결과는 Issue #1에 날짜와 함께 추가한다. 별개 문제라면 새 Issue를 만들고 Issue #1을 연결한다. 사용자가 직접 작성할 필요 없이 ChatGPT에 기록을 요청해도 된다.

기록 항목은 ‘증상 → 확인 근거 → 원인 또는 미확정 사항 → 변경 → 검증 → 실제 적용 여부 → 남은 확인’ 순서로 한다. 이전 관측을 현재 결과로 덮어쓰지 않는다. 실제 발송/수신 확인과 발송을 차단한 시험은 구분한다.

수정은 별도 브랜치와 PR에서 검토하고, 관련 오프라인 검사와 필요한 읽기 전용 실조회·발송 차단 검증을 수행한다. 운영에 적용할 때는 현재 파일 해시 확인 → 서비스와 같은 flock 잠금 확보 → 백업 → 적용 → 구문/해시 확인 → 다음 정상 예약 실행 확인 순서로 진행한다. 필요하면 실제 전달 결과를 별도로 확인한다. 수동 재발송은 명시적 요청이 있을 때만 한다.

## 5. 복구와 완료 기준

문제가 악화되면 당시 백업과 현재 해시를 대조해 복구 범위를 정한다. 진단 기능만 되돌리는 백업과 공동도급지역 수정 전체를 되돌리는 백업은 다르므로 [manifest](../manifest.json)와 적용 기록을 먼저 확인한다. 서비스 잠금을 확보한 상태에서 해당 파일만 복원하고 중복발송 기록은 보존한다. 전체 발송 프로그램 복원에는 별도 보관한 비공개 원본이 필요하다.

해결 여부는 수정 파일, 검사 결과, 운영 적용 시각/백업, 적용 후 예약 실행 및 필요한 실제 수신 확인을 근거로 기록한다. 확인하지 못한 항목은 미완료로 남긴다. Issue #1에 남은 개선 항목이 있으면 계속 열어 둔다.

이 절차서는 2026-10-23에 작성했다. 절차서 추가만으로 운영 프로그램·예약·발송은 변경되지 않는다.
